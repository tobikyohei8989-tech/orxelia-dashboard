# ORXELIA Stripe連携計画（販売事業決定後に着手）

更新日: 2026-11-07
状態: 計画のみ。Stripe本番連携・課金・公開は未開始。

## 着手条件
- ORXELIAで販売対象の最初の事業をユーザーが最終承認した後にのみ着手する。
- 事業選定前にStripe商品・料金・決済リンク・本番課金・Webhookを作成しない。
- テスト環境での動作確認後、ユーザーの別途明示承認を得て本番設定する。

## 複数事業の識別と管理
- ORXELIA内部の不変な事業UUIDを基準とし、Stripeのproduct_id / price_idと対応付ける。
- 同一事業の複数プラン、料金改定履歴、月額/年額、契約のステータスを管理する。
- Stripeの商品metadataにORXELIA事業IDを設定する。ただしmetadataだけを唯一の照合元とせず、Supabaseの対応表を正本にする。
- 原則、同一Stripeアカウント内の商品単位で事業別集計する。事業ごとにStripeアカウントを分ける必要性は法人・会計・税務・リスクの要件を確認して判断する。

## 管理指標
- 事業別：有効契約数、新規契約、解約、月額経常収益(MRR)、請求額、入金額、返金、未払い、決済手数料、変動費、固定費配賦、税引前の利益見込、利益率。
- 全事業合計と事業別の内訳をホームに表示し、詳細画面で月次推移・料金プラン別・解約率を確認する。
- MRR、売上、入金、利益は別の指標として扱う。未連携・未入力はゼロ扱いしない。
- Stripeに存在しないAI API費、サーバー代、広告費、人件費、返金関連コストはORXELIA側で入力・配賦する。
- 契約数はStripeのサブスクリプションから事業別に集計し、現在の端末ローカル営業記録の「契約」件数を正式契約数に流用しない。

## 技術設計
- Supabase: business_stripe_products（事業ID↔Stripe商品/価格ID）、subscription_snapshots、billing_events、cost_entries、sync_status等の構成を設計。
- Stripe Webhook: 署名検証、イベントID重複排除、再送・順不同対応、定期照合、監査ログ、失敗通知。
- Stripe秘密鍵・Webhook署名シークレットはサーバー側のシークレット管理のみ。GitHub Pagesや公開JS、DB公開カラムに保存しない。
- RLSで所有者だけが事業・収益情報を閲覧できるようにし、Webhook受信は安全なサーバー側で処理する。
- 事業別に収益と費用の実績・見込・未確定を区別。円単位、タイムゾーン、税込/税抜、手数料、返金の集計基準を決める。

## 実行順序
1. 初の販売事業が確定し、販売承認を確認する。
2. 事業ID・料金・決済主体・税務・返金規約を確定する。
3. Stripeテストモードで商品/価格とSupabase事業IDの対応表を構築。
4. 契約/決済/解約/返金のWebhookを実装し、異常系・重複・再送テスト。
5. ORXELIAホームに全事業合計と事業別契約数/売上/利益を表示し、Stripeと照合。
6. ユーザーの明示的な本番移行承認を受けて本番設定・公開する。

## 継続的な方針
- 事業の追加時は同じ連携方式を再利用し、事業間の数値を混同しない。
- ユーザーの許可なく商品作成、課金、販売開始、公開をしない。
