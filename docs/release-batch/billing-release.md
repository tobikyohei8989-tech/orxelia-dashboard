# Partner Linkの契約連携を公開する前の確認

今回の実装は開発ブランチに保存する。実際のStripeテスト環境とSupabaseのサーバー関数を組み合わせた確認を公開前に行う。接続済みのStripeアカウントは現時点で本番のみ。手元のテストは架空のStripe応答とPostgreSQL互換環境を使用した。

## 適用順

1. テスト環境の既存Partner Linkスキーマを確認する。ダッシュボードの法務審査・開発依頼・販売記録・手動同期・案件状態更新のSQLを適用する。案件状態更新は法務審査の後に適用する。
2. `integrations/partner-link-billing/` の `customer-management.sql`、`registration.sql`、`reconcile.sql`、`partner-access.sql` を順に適用する。通知キューの適用履歴を確認し、新規環境では `queue.sql` を適用してから `worker.sql` を適用する。既存のキューと通知履歴は保持する。
3. 通知受信、契約状態処理、申込・契約管理の3つの関数を配置する。通知受信はStripe署名、契約状態処理は専用トークン、申込・契約管理はログイン済みの認証情報と会社の所有者情報で認証する。各関数の認証に合わせてゲートウェイのJWT検証を設定する。
4. Stripeアカウント、環境、料金ID、サイトのオリジンを対象環境に合わせる。秘密鍵・通知署名・契約状態処理の専用トークンはサーバーのシークレットに保存する。Vaultの `partner_link_billing_worker_url`、`partner_link_billing_worker_token` に同じ対象環境を設定してから `worker-schedule.sql` を適用する。定期呼び出しの利用量を利用枠に照らして確認する。[Supabaseの関数スケジュール設定](https://supabase.com/docs/guides/functions/schedule-functions)
5. 顧客管理担当者を管理者一覧へ登録し、会社登録と認証メール、申込、30日無料、初回決済、更新失敗、復旧、解約、返金・紛争、会社間の分離を検証する。PC・スマホ表示、iPhone通知、既存社内会社、実業務の人工登録も確認する。公開前に利用条件・プライバシー表示と支払失敗後の猶予方針を確定する。
6. 公開対象・確認結果・復旧手順・費用を提示して承認を得る。承認後に同じ一括公開へまとめる。顧客向けの申込受付は `PARTNER_LINK_BILLING_ENABLED` を明示的に有効にして開始する。

## 確認できたことと残作業

- 2026-11-11に本番料金を読み取りで確認。税込3,980円、日本円、毎月、料金に税を含む設定。申込時の税自動計算はオフ。
- 手元では、会社登録、申込受付前のエラー、契約管理画面の遷移先の検証、通知の再試行、重複返金の防止、契約終了時のデータ取得・更新の拒否、既存社内利用を確認した。
- 紐付けが一意の返金は自動記録し、紛争・不正利用・複数の請求書にまたがる返金は確認対象として扱う。確認対象の契約では、必要に応じて管理者が理由・期限付きで利用停止を記録できる。
- 実際のStripe通知と支払い画面、クラウド側の定期起動、既存の通知配信経路、実機の確認は残る。現行の法務文書の確定と事業ID・収支の整合は一括公開の作業記録を参照する。

## 復旧

申込受付の問題は、受付フラグをオフにして新規申込を止める。処理側に問題がある場合は、対象の定期実行を停止し、通知キューと取引記録を保持して調査する。契約処理が直ったら未処理の通知を再照合する。既存の会社分離と利用権限を保った状態で、直前の確認済み画面へ戻せることを公開前に検証する。
