# ORXELIA 顧客・契約・利用権限の共通基盤

2026年11月10日／一括改善への追加設計

状態：設計。Stripe接続、商品・料金作成、DB変更、実際の課金、本番公開、既存利用者の停止は未実施。

## 最初の画面

既存ダッシュボードに「顧客管理」を1項目追加。中は「顧客一覧」「契約・売上」「利用制御」の3つにまとめる。顧客管理・契約・売上・決済・利用権限の5機能は、この3画面と詳細パネルで扱い、トップメニューを増やしすぎない。

上部は「契約顧客数」「契約月額合計」「支払要確認」の3項目。月額契約の合計を実際の入金と混同しないよう、「月額売上」という曖昧な名前を避ける。詳細画面でMRRと当月決済成功額・返金額を分けて表示する。

Stripe未接続は「未接続」、未取得は「未取得」と表示し、0社・0円とはしない。サンプルはデモ専用画面に隔離し、架空であることを常時表示する。提示された3社・7,440円は実績登録しない。

## 最小機能

| 機能 | 初期の範囲 |
|---|---|
| 顧客 | 会社名、担当者・連絡先、登録日、契約アプリ。1社が複数アプリを契約できる。 |
| 契約 | アプリ、プラン、月額/年額、状態、支払済み期限、次回請求予定、解約予約。契約と利用権限を別に持つ。 |
| 売上 | 月次・年次・アプリ別の決済成功額、返金額、返金控除後の決済額。契約月額・MRR・銀行入金とは分ける。 |
| 決済 | 成功、失敗、要確認、返金、解約の履歴。カード番号等はORXELIAに保存しない。 |
| 利用権限 | アプリ単位の有効、猶予中、停止、解約予約。管理者例外は理由・期限・履歴付き。 |

継続率・解約率は将来追加できる履歴を残す。初期画面には増やさない。顧客単位の解約とアプリ契約単位の解約、期間初の母数、新規顧客の扱いを決めてから計算する。年額の月割り、割引、税、異なる通貨、未払いをMRRに含める範囲も明示する。最初は単一通貨JPY、固定月額、1アプリ1契約を基本にする。

## 共通の識別と構成

- ダッシュボードの事業IDをアプリIDへ対応付け、開発案件と販売アプリの二重登録を防ぐ。
- 契約主体は会社・個人の顧客ID。ログイン利用者は所属情報で会社へ紐付ける。会社IDとログインユーザーIDを混同しない。
- 顧客ID×アプリID×契約IDで利用権限を管理。同じ会社の別アプリまで停止しない。契約作り直し・移行を考慮し、旧契約の通知だけで新契約を止めない。
- Stripeは請求・契約・決済の事実を管理。Supabaseはその対応表・同期情報と利用権限を保持。ORXELIA管理者の権限と顧客会社の管理者権限は別にする。
- 管理画面は独立したモジュールとし、管理者専用APIから最小限の情報を取得する。画面を非表示にするだけで管理者専用とはしない。
- 既存の開発・承認・収支記録、Partner Link、ホームページの挙動を一括で切り替えない。既存の手動売上とStripe決済を二重計上しない。

初期の保存対象はアプリ対応表、顧客、所属、契約、請求/決済/返金、利用権限、Webhook受信処理、期限付き例外、監査履歴、照合状態。既存テーブルの流用可否と権限を確認してからDB設計を確定する。テストと本番のデータ・秘密情報を分離する。

## 利用開始・停止ルール（初期仕様案）

| 状況 | 方針 |
|---|---|
| 初回契約・支払未完了 | 未開通。登録や決済完了画面だけで利用権限を与えない。 |
| 初回支払成功・契約条件を満たす | 該当アプリの利用開始。 |
| 更新支払成功 | 支払済み利用期限を更新。 |
| 更新支払失敗 | 適用対象となる最初の失敗から7日間の猶予を仮案とする。支払済み期限は尊重し、再試行や重複通知で猶予を延ばさない。 |
| 支払済み期限と猶予の両方が終了・未解消 | 該当アプリを停止。データは削除しない。 |
| 必要な支払の解消・契約有効 | 自動復旧。ただし管理者による停止や他の未解消条件は上書きしない。 |
| 期間末解約 | 支払済み利用期限まで利用でき、終了後に停止。 |
| 一部/全額返金、紛争、複数未払い | 単純な成功/失敗だけで判断しない。対象期間と契約を確認し、初期は管理者確認対象とする。 |

7日はStripeの固定仕様ではない。Stripeの再請求・最終状態の設定、契約条件、通知方針と揃えてから確定する。試用期間と即時解約は初期の標準導線に入れず、追加する場合は別の利用ルールを定める。

停止後も、ログイン、支払情報更新、請求書確認、問い合わせ等の復旧経路は利用できるようにする。お客様向けの停止画面から、その顧客・契約に限定したStripe Customer Portalへ移動する。顧客IDをブラウザーの任意入力だけで決めない。

## サーバー側の連動

1. 署名を検証したStripe通知を受信し、受信環境と対象アカウントを確認する。
2. イベントIDで重複を排除し、確実な保存後に処理する。保存失敗・処理失敗を再試行できる構成にする。
3. 通知が古い・順不同でも契約状態を巻き戻さないよう、現在のStripe状態と請求対象を照合する。
4. 契約・支払済み期限・猶予・管理者例外から、顧客×アプリの利用権限を再計算する。
5. 定期処理で猶予期限を判定し、通知欠落や同期不整合も照合する。失敗時に完了扱いしない。
6. アプリのデータ読取・更新APIとDBの権限判定で利用権限を適用する。必要なStorageやリアルタイム経路も確認する。

ブラウザーから契約状態・支払状態・管理者権限を書き換えられないようにする。秘密鍵や署名シークレットはサーバー専用。単純に「通知がしばらく来ない」だけで全顧客を停止せず、既知の支払済み期限と権限を使って判断する。管理者操作・復旧・例外は監査できるようにする。

## 最初に接続するアプリ

Partner Linkは候補。ただし、現在の社内利用を一律で有料契約必須に切り替えない。最初は独立したテスト用会社・テスト用アカウントで動作確認する。社内利用は期限・根拠のある社内利用区分として、顧客の有料契約と区別する。

確認ケース：初回失敗で未開通、成功で開通、更新失敗、7日経過、決済復旧、解約予約・期間終了、二重通知、逆順通知、通知欠落、管理者停止の維持、他アプリへの非波及、別会社へのアクセス拒否、既存社内利用への非影響。

## 実施順と公開

1. 共通事業ID、顧客・契約・権限モデル、画面の設計を既存の一括改善案へ統合する。
2. 未接続状態とデモを分けた画面、人工データによる契約・停止・復旧のテストを開発ブランチで作る。
3. ユーザーのStripe設定後、本番と分離されたStripeテスト環境とテスト用DB/スキーマへ接続する。新規連携は原則Stripeの独立したsandboxを使う。
4. 最初の1アプリでサーバー側の利用制御を検証する。
5. プレビュー、テスト結果、データ移行、影響範囲、公開先を提示し、承認後にダッシュボードをまとめて公開する。
6. 実課金と既存アプリの利用停止制御の有効化は別の明示承認を得る。検証済みの方式を他アプリへ順次展開する。

一括公開で削減できるのはNetlifyへの公開回数。Stripe設定、DB移行、テストと本番の切り替え、アプリごとの権限制御を1回の画面公開だけで完了扱いにはしない。
