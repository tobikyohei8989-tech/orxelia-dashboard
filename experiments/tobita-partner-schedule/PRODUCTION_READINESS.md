# 職人マッチング 実用化チェックリスト（2026-11-08）

## 現在の状態
- 実験ブランチにカレンダー、複数日打診、職人承諾即成立、管理者取消、進捗タブを実装。
- 試作品のデータはブラウザ localStorage。別端末間では同期されない。
- Supabase public.tobita_partners / tobita_jobs / tobita_assignments / tobita_availability / tobita_notifications が存在し、RLS有効。
- 既存のRLSは owner_id=auth.uid()。これだけでは別アカウントの職人に依頼を見せられない。
- 出勤・人工・請求機能は対象外。既存テーブルは他機能への影響を避けるため削除しない。

## 必須の実装と受入試験
1. **認証と所属**
   - Supabase Authのメール認証を利用。管理者と職人を分離。
   - 管理者が招待した職人だけ所属できる。管理者以外は招待・権限変更不可。
   - 既存のowner_idによる管理者データ保護を維持し、職人には本人に割り当てられた情報だけ公開。
   - RLSで他職人の予定・案件・連絡先へのアクセスを拒否することを、2職人+管理者の別セッションで検証。
2. **同期**
   - localStorageを本番の正本にしない。Supabaseを唯一の正本とする。
   - 空き登録・打診・承諾・取消はサーバー側のトランザクション/RPCで処理。
   - 重複打診、同時承諾、午前午後の重なり、確定後の職人側取消をDB側で拒否。
   - Realtimeを購読し、切断後の再取得も実装。
3. **通知**
   - 打診は職人、承諾・辞退は管理者、取消は双方へ通知。
   - アプリ内通知を先に実装。プッシュは許可取得・端末登録・配信基盤・実機検証が必要。
   - 通知失敗でもDBの確定状態は失われない設計。
4. **複数日**
   - 全日空きの職人のみ選択。現場名・時間帯を指定し、一括打診。
   - 日ごとに承諾/辞退可能。将来の一括承諾は別仕様として扱う。
   - 一括処理中に他者が同じ枠を押さえた場合は、DBで整合性を守り、失敗日を表示。
5. **端末・セキュリティテスト**
   - 管理者PC、職人iPhone、別職人iPhoneの3セッションでE2E。
   - 不正アクセス、重複操作、通信断、通知拒否、月跨ぎ、半日枠、日本語入力、取消確認を検証。
   - 本番公開・招待メール送信・通知送信・費用発生は、明示的な許可まで行わない。

## リリース判定
**未達（試作品）**。現在のlocalStorage版を実際の手配の唯一の記録として使用しない。
GitHub ActionsでのJS構文確認や模擬DOMテストは、認証・同期・実機の合格を意味しない。
